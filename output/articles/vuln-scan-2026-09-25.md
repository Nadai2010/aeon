## Confirmed finding (routed to PVR)

**Script-Fu code injection via unvalidated numeric layer fields (HIGH, CWE-94)**

`gimp export render` builds a single GIMP Script-Fu batch script by string-formatting layer fields into the script source. String fields (`name`, `text`, `font`) are correctly escaped via the repo's own `_script_fu_escape()` — but the numeric fields (`width`, `height`, `opacity`, `offset_x`, `offset_y`, `font_size`) are spliced in unescaped and unquoted, with no check that they're actually numbers. The project loader (`open_project()`) only validates that a `.gimp-cli.json` file has `"version"` and `"canvas"` keys — it does not validate `layers` at all. So a crafted project file with a string instead of a number in one of those fields results in that string being evaluated as Script-Fu source by the real `gimp` batch process. Script-Fu can do arbitrary file I/O, so this reaches at least arbitrary file read/write with the privileges of the process running `gimp-cli`.

This is precisely the risk class the maintainers already documented and partially mitigated in `SECURITY.md` ("Script-Fu injection... Mitigation: `_script_fu_escape()` in `gimp_backend.py`") — the escape function is correctly implemented for the fields it covers; the gap is that it isn't applied to the numeric ones. The identical vulnerable pattern is duplicated across the vendored `cli_anything` copy under every other tool integration in this monorepo that shares this GIMP harness code.

- **Severity:** HIGH (CWE-94, code injection → file read/write; not confirmed as direct RCE)
- **PoC verification:** `verified` via `./scripts/vuln-poc-gate.sh command`, local-command verifier. The verifier calls the real, unmodified `render_project()` production entrypoint directly (only the actual `gimp` subprocess call is stubbed, since GIMP isn't installed in this sandbox — the vulnerability is entirely in how the Script-Fu source text is built *before* that call, so stubbing the subprocess doesn't touch the code under test). The attacker's chosen Script-Fu form appeared verbatim and unescaped as an independent expression in the generated script; a control check in the same run confirmed the `name` field *is* correctly escaped, isolating the gap to the numeric fields. Result bound to commit `34f519533bc175d2fe287ab8316b0dd99bb9cc43`, `finding_sha256: 2f38a0d09c5c82f4211c01a659d3d3788961e682c0ca7b051ee931a7647dce5d`.
- **Channel:** PVR (correct per SECURITY.md). Submission attempted and blocked by token scope (see Environment note above) — staged at `memory/pending-disclosures/HKUDS-CLI-Anything-2026-09-25.md` with the full report payload ready to submit.
- File/line and full exploit detail are withheld from this report per PVR disclosure policy — see the staged draft (private) for the complete write-up.

## Reviewed and dismissed (not findings)

- `eez_studio_backend.py` — semgrep flagged tainted `subprocess.run` args, but the command comes from a local, operator-set `EEZ_STUDIO_BUILD_COMMAND` env var (documented opt-in escape hatch), not attacker-reachable input.
- `.github/workflows/pr-labeler.yml` — semgrep flagged `pull_request_target`, but it checks out `base.ref` (not the PR head) with `persist-credentials: false` and runs only base-repo scripts — the textbook safe pattern, not the vulnerable one.
- `.github/scripts/validate_root_skills.py` — `exec()` flagged, but it loads a sibling first-party script file, not external input.
- `unimol_backend.py` — `pickle.load()` flagged, but it reads a `metric.result` file the same training process just wrote to its own `save_path`, not untrusted network data.
- `obsidian_backend.py` — `verify=False` (×6) on `requests` calls, but explicitly documented and scoped to the Obsidian Local REST API plugin's self-signed `https://localhost:27124` — standard practice for this class of local-loopback plugin API.
- `cli-hub/cli_hub/installer.py` + `registry.py` — `shell=True` fires for install commands containing shell operators, sourced from `registry.json`/`public_registry.json` fetched from `hkuds.github.io`. `CONTRIBUTING.md` documents these as human-reviewed PR-gated entries — the same trust model as Homebrew/apt package registries, not a novel vulnerability.
- `melt_backend.py` (kdenlive/shotcut) — SECURITY.md's documented codec-allowlist mitigation (`ALLOWED_VCODECS`/`ALLOWED_ACODECS` + `_validate_extra_args` blocking `vcodec=`/`acodec=`/`-consumer` overrides) is correctly implemented; commands run via list-form `subprocess.run` with no `shell=True`.
- 24 semgrep `use-defused-xml` hits (drawio, inkscape, shotcut, libreoffice, musescore, kdenlive, calibre, 3MF, krita, macrocli, zotero) — spot-checked the modules that actually parse untrusted external files (SVG/MLT/ODF/MSCX); all correctly use `defusedxml.ElementTree.parse`/`fromstring` for the untrusted-input path. The semgrep rule fires on the mere `import xml.etree.ElementTree` (used for safe XML *building*, not parsing) in the same files — false positive.
