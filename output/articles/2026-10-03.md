# A Repo With No Commits in 11 Weeks Just Had Its Best Day Ever

`pablostanley/yoinks` — a terminal tool for ripping videos off YouTube, X, and about 1,800 other sites — hasn't been pushed to since July 17. Today it pulled 623 new stars, its single biggest day since launch, on its way to 3,683 total. Nobody shipped a feature. Nobody fixed a bug. The spike is pure word-of-mouth, three months after the author stopped touching the code.

That's not an anomaly — it's the default state of a growing share of GitHub's most popular software.

## The number that explains it

[A recent audit of 848 installable AI repositories with 10,000+ stars](https://olud.ai/blog/dormant-ai-repos-2026/) found that 223 of them — 26% — haven't taken a commit in over a month. Sixty-three have gone a full year without one, and between them they still hold 1.27 million stars. `nomic-ai/gpt4all` sits at 77,402 stars after 432 days of silence. `lencx/ChatGPT` has 54,401 stars and hasn't been touched in 703 days.

The line that cuts to the point: "A star is permanent... the last commit date is not permanent. It is the one number on a GitHub page that tells you whether anyone is still home."

Yoinks is the small, fresh version of the same pattern: [its GitHub API record](https://github.com/pablostanley/yoinks) shows `pushed_at: 2026-07-17`, one day after the repo was created. Everything since — the forks (320), the open issues (21), the stars climbing past 3,600 — happened without a single line of new code landing.

## Why some languages dormant faster than others

The audit breaks dormancy down by language, and the split is stark: Python repos go quiet at 36%, JavaScript at 32%, versus Go at 7% and Rust at 16%. The explanation isn't language ergonomics — it's what each language is typically used for. Python is where research prototypes live: "the code gets 30,000 stars in a fortnight, the authors graduate, and the repository is done." Infrastructure code written in Go tends to stay alive because, as the audit puts it, "that kind of project either has someone running it in production or it has no stars at all" — no stars means no incentive to abandon it publicly, and production use means someone has to keep patching it.

Yoinks, a TypeScript CLI with no backend to run in production and no research claim to defend, fits neither pole — it's a utility that worked well enough on day one that it didn't need day-sixty maintenance to keep spreading.

## The weekly machine that keeps finding these

This isn't a single freak event — it's a standing feature of how GitHub attention moves now. Newsletter roundups like [buildwithneej's weekly repo digest](https://buildwithneej.substack.com/p/5-github-repos-that-went-nuts-this) track five new breakout repos every single week, collectively pulling around 17,000 stars in seven days — and the roster mixes actively-shipping projects with ones running on fumes. Discovery has decoupled from development velocity: a repo doesn't need new commits to resurface, it just needs to get mentioned in the right thread, newsletter, or group chat at the right moment.

## What this means if you're the one evaluating a tool

Star count has quietly become a lagging indicator of *past* word-of-mouth, not a live signal of *current* maintenance. If you're picking a dependency off a trending list, the stat that actually tells you something is `pushed_at`, not `stargazers_count` — the gap between those two numbers is exactly where "popular" and "maintained" stop meaning the same thing. Yoinks might keep climbing for months without another commit. That's fine for a weekend CLI tool. It's a different conversation entirely if the repo you're trusting is infrastructure.
